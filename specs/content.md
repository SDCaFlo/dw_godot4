# Content architecture (design)

How game content (Digimon, techniques, items, maps, models, text, …) is organised so that the original game, our own additions and, later, mods all go through the same path. This is a design document: it fixes the rules the porters, `GameData` and the game systems follow from now on. Status of each part: `PLANS.md`.

Decided 2026-10-23. Scope now: build the foundations so modding stays possible (§1–§6). Modding itself comes last (§7).

## 1. Content packs

All content lives in **packs**. A pack has an id, a manifest, data tables and assets.

| Pack | What | Where | Committed? |
|---|---|---|---|
| `dw1` | the original game, generated by the two porters from your disc dump and the decomp | `asset_porter/output/`, `data_porter/output/` | never (game content) |
| own packs (later) | our additions: new Digimon, items, techniques, models | `res://content/<pack>/` | yes, if the content is ours |
| mods (later) | third-party packs | a mod folder | no |

- **Manifest** (`pack.json`): `id`, `name`, `version`, `depends` (e.g. `["dw1"]`), `load_after`. The `dw1` manifest is written by the data porter and points to both porter output folders.
- **One schema.** A pack's data tables use the table shape the data porter writes (`data_porter/CLAUDE.md`, "Output"). An added pack may omit the source-only keys (`source`, `used_by`, `c`).
- The game never asks whether something is original. It asks the registry (§4) for a Digimon, an item or a model, and gets it from whichever pack defines it.

## 2. Keys

Every content record has a **key**: a namespaced string id, `<pack>:<name>`, lowercase `a-z 0-9 _`.

- Savegames, packs and new game code refer to content by key.
- The original numeric ids stay as **aliases inside `dw1`** (Agumon = 3), because the original event scripts, map files and tables reference them. `GameData.digimon(3)` and `GameData.digimon("dw1:agumon")` return the same record.
- New packs' records have no numeric id unless they need one to work with the original scripts (see §7, open question).

### Key rule for `dw1` (data porter)

Keys come from the C string id of the record's name, which the decomp already keeps unique and readable:

- **name** = the string id without its prefix, lowercased: `STR_DIGIMON_NAME_AGUMON` → `dw1:agumon`, `STR_DIGIMON_NAME_NPC_GREYMON` → `dw1:npc_greymon`, `STR_ITEM_NAME_SM_RECOVERY` → `dw1:sm_recovery`, `STR_TOURNAMENT_NAME_GRADE_A` → `dw1:grade_a`. The prefix is `STR_<KIND>_NAME_` of that table.
- **Several records sharing one string id** (the decomp points them to one string): each of them gets `_<id>`. Techniques: `dw1:dynamite_kick_44`, `dw1:dynamite_kick_48`, `dw1:horizontal_kick_55` / `_57`, `dw1:bubble_113`, `_118`, `_119`, `_120`.
- **Records with no name string**: `<kind>_<id>` (technique 121 → `dw1:move_121`).
- **Maps** use their file name: `dw1:mayo01`. The area name is shared by many maps (18 maps are "Native Forest"). Two entries use the same file (`YAKA25`, ids 65 and 232: `dw1:yaka25_65`, `dw1:yaka25_232`), and 11 unused entries have no file (`dw1:map_239` …).
- **Per-Digimon tables** (`raise_data`, `sleep_patterns`, evolution requirements / gains / paths, cards, file names, sounds, item take distance) don't get keys of their own: they are **components** of the Digimon entity (§3) and reference its key.
- The porter checks that keys are unique per kind. A collision fails `convert`.

Key kinds (separate namespaces, so `dw1:meat` can't clash with a Digimon key): `digimon`, `move`, `item`, `map`, `tournament`, and more as systems need them.

## 3. Entities and components

The C code spreads one Digimon over many parallel arrays indexed by the same id. For content, one Digimon is **one entity** with **components**:

| Entity | Components (current tables) |
|---|---|
| Digimon | `digimon` (`digimon_data`), `files` (`file_names`), `sounds` (`sound_ids`), `care` (`raise_data`, `item_take_distance`, sleep pattern), `evolution` (`requirements`, `paths`, `stat_gains`), `card` (`card_data`), `enemy_music` |
| Technique | `move` (`move_data`), `learn` (`learn_chances`) |
| Item | `item` (`item_data`), `effect` (`item_effects`), `evolution_target` (`item_targets`) |
| Map | `map` (`maps`, plus the asset porter's `maps/<NAME>/`), `toilet`, `training_spots` |

- In `dw1` the components stay in their tables (the porter output stays a lossless mirror of the decomp). The registry assembles the entity view.
- A new pack adds a Digimon as one entity record with the components it needs. Components it omits are "absent": a Digimon with no `card` simply has no card, one with no `care` can't be a partner.
- Tables that aren't per-entity (type factors, flee chances, battle commands, the tournament schedule) stay tables. Packs patch their records (§5).

## 4. Logic reads properties, never id ranges or counts

The original code identifies kinds of content by **id ranges and literal ids**, and sizes by **array lengths**. Examples from the specs:

| Original rule | Where | Becomes the property |
|---|---|---|
| techniques `0x00–0x39`, finishers `0x3a–0x70`, Counter `0x2d`, generic `0x79` | `specs/moves.md` §2 | `move.kind`: `technique` / `finisher` / `counter` / `generic` / …; `move.learnable` |
| one learn-chance row per technique `0x00–0x39` | `specs/moves.md` | `learn` component present |
| partners are ids 1–65 (`ITEM_TAKE_DISTANCE[id - 1]`, `RAISE_DATA[66]`) | `specs/digimon.md` | `care` component present (`digimon.partner` already exists) |
| HP / MP items `0–6` index `HEALING_VALUES` by id | `specs/items.md` | the `effect` component carries its values |
| evolution items `< 0x7d` index `EVOLUTION_ITEM_TARGET[id - 0x47]` | `specs/items.md` | `evolution_target` component |
| Numemon `11` fallback, Sukamon `0x27`, Nanimon `0x35`, fixed Fresh targets, special evolutions | `specs/evolution.md` §2 | evolution rule properties (e.g. `fallback_evolution`, `virus_bar_target`) or rule records |
| 180 Digimon, 128 items, 122 techniques, 66 cards | every spec | no fixed counts: iterate the registry |

Rules:

- **The porter derives the property** from the original rule and checks it (`out.check`), so the `dw1` behaviour is unchanged. The spec of the table documents both the property and the original C rule.
- **The GDScript port tests the property**, and its comment names the C function and the original condition (`# BTL_…: move id >= 0x3a`).
- **Original quirks stay**: they become data or a documented branch, not lost behaviour (e.g. the medal-order quirk, the evolution averaging quirk).
- When porting a system, every id or count literal in the C code is either turned into a property or listed in the spec as a deliberate `dw1`-only rule.

## 5. Record-level merging

Packs are applied in load order (`dw1` first, then by `depends` / `load_after`). A pack table can:

- **add** records (new keys);
- **patch** records: `{"key": "dw1:meat", "patch": {"price": 80}}` changes only those fields (nested dictionaries merge, arrays replace);
- **remove** a record: `{"key": "…", "remove": true}` (rare; may break content that references it).

The registry keeps, for every record, which packs changed it (for debugging and for the dock).

The current `GameData` mod folders (whole-file replacement) are the first step. They are replaced by this once packs exist.

## 6. Assets: one loader, two sources

Content refers to assets by **pack-relative paths** (`dw1` → `mmd_files/MMD0/AGUM.gltf`), resolved by one loader (`Content`, the successor of `PorterAssets`):

1. a **Godot-imported** copy under `res://content/<pack>/…` if present (editor and own packs: import settings, thumbnails, drag and drop, animation preview);
2. otherwise the **raw file** (glTF, PNG, WAV/OGG, JSON) loaded at runtime, as `PorterAssets` does now.

- **`dw1` in the editor:** a local step mirrors a selection of the asset porter output (models, maps; not movies) into `res://content/dw1/`, which is **gitignored** and has no `.gdignore`, so Godot imports it. Scenes may reference those paths; the files themselves are never committed. Someone without the output gets a missing resource until they run the porters, which they need to do anyway.
- **`dw1` in an exported game:** Godot's importer doesn't exist there, and the export must not contain game content. The game loads `dw1` raw from the player's generated folders (source 2).
- **Own packs:** imported in `res://content/<pack>/` and committed, if the content is ours.
- **Editor rule (unchanged):** a preview never writes content into a tracked file (`PLANS.md`, "Rule").

## 7. Modding (later)

Modding comes last, but the parts above are built so it needs no rewrite. To do then:

- **Mod formats:** both raw-file packs (a folder with `pack.json`, JSON tables and glTF / PNG / OGG; no Godot needed) and `.pck` packs built in the Godot editor (`ProjectSettings.load_resource_pack`).
- **Model contract** for models from other games or tools: animation names mapped to what the game requests (idle, walk, run, hit, the technique slots — `0x2e + slot` in the original), scale, pivot / root, collision radius and height from the Digimon record, texture rules. The asset porter would name the original animations to the same contract.
- **"DW Data" dock as the modding tool:** browse the merged registry (all packs), see which packs changed a record, "duplicate `dw1:agumon` into `mypack`", edit, preview the model, and write the pack's JSON.
- **Open questions:**
  - New content in original event scripts (e.g. a new Digimon in a shop or a script check) needs a numeric id or a script extension.
  - Keys go into savegames: if the decomp renames a string id, the `dw1` key changes. Possible fix: a key lock file in the data porter, which keeps keys once issued.
  - Load order conflicts between two mods patching the same field.

## Order of work

1. This spec.
2. Data porter: keys (§2) and the `dw1` pack manifest; property flags (§4) added per system when that system is ported (moves `kind` / `learnable` first).
3. `GameData` as the registry: packs, key lookups next to numeric aliases, entity view, record merging (§3, §5).
4. `Content` loader and the `res://content/dw1/` mirror (§6), the editor visibility step from `PLANS.md`.
5. Game systems, written against properties and keys from the start.
6. Modding (§7).
